## 0. 先把丑话说在前面（三条硬约束）

在动手之前，有三件事必须先接受，否则整个项目会在第 3 周崩掉。

### 约束一：**1,000,000 个个体在屏幕上不可能"各自可辨"——这是像素的物理限制**

| 分辨率 | 总像素 | 100 万个体每个能分到 | 观感 |
|---|---|---|---|
| 1920×1080 | 2.07 M | **2.1 px** | 一颗灰点，完全无法分辨 |
| 2560×1440 | 3.69 M | 3.7 px | 2×2 的亮点 |
| 3840×2160 | 8.29 M | 8.3 px | 3×3 的小块 |

也就是说：**在 1080p 上，100 万个个体即使铺满整个屏幕、彼此零重叠，每个也只有 2 个像素。**

这个数学事实决定了三件事：

1. 省级视角下的"百万尸潮"**必须**用**密度场/点云/热力图**来表现，不管你显卡多强；
2. "个体渲染"只在相机贴近地面时才有意义（那时视野里只有几千个个体）；
3. 讽刺的是——**百万级的视觉效果，恰恰回到了 2009 年的"红绿点"**。这不是退步，这是唯一正确的解。我们要做的是把"点"做到极致美（发光、拖尾、密度云、流动线），而不是徒劳地给 100 万个人建模。

### 约束二：**1,000,000 个带蒙皮动画的网格 = 不可能**

| 方案 | 三角形总量 | 可行性 |
|---|---|---|
| 100 万个 300 面人形 + VAT 动画 | 3 亿三角 | ❌ 顶点吞吐/带宽直接爆，且 100 万个实例的动画采样也无意义（看不见） |
| 100 万个 2 面点精灵/quads | 200 万三角 | ✅ 毫无压力（GPU 处理能力绰绰有余） |
| 2 万个人形 + 98 万个点精灵 | 600 万 + 196 万 | ✅ 这才是正解 |

**结论：外形要分层。近处是有血有肉的人，远处是发光的点。中间没有渐进过渡，是硬切换——但切换阈值按"屏幕像素尺寸"算，人眼看不出来。**

### 约束三：**"一个省的地图"≠"一个省的 3D 建筑"**

- 一个省 10 万 km²，若按 1km² 有 2,000 栋楼算，全省约 **2 亿栋**建筑。存不下、也画不动。
- 而且省级视角下建筑是亚像素的，画了也看不见。
- **结论：地图必须做成"金字塔"，每一级只有该级该有的数据**（详见 §2）。

> 一句话总括：**你真正要的不是"100 万个能看见的僵尸"，而是"100 万个真实存在、会传播、会淹没城市的僵尸，并且在任何缩放级别下都呈现得当"。** 这是可达成的（而且很爽）。"100 万个人形模型同框"是不可达成的。两者的区别就是本报告的全部内容。

## 2. 世界模型：四层金字塔

```
┌──────────────────────────────────────────────────────────────┐
│ L0  统计层   全国 / 大区        5 km 网格    ~38 万格         │
│     SIR+PDE 疫情扩散 + 城际通勤流 + 行政区              │
├──────────────────────────────────────────────────────────────┤
│ L1  区域层   省 / 城市群        1 km 网格    ~960 万格（全国）│
│     更细的 PDE + 公路/铁路传播 + 城市级人口账本           │
├──────────────────────────────────────────────────────────────┤
│ L2  群体层   城区街区           50 m 网格    视口内激活       │
│     街区级「人群团」（1 团 = 10~100 人）+ 路径 + 士气     │
├──────────────────────────────────────────────────────────────┤
│ L3  个体层   相机 2 km 内       米级         ~2 万个体       │
│     完整的 v1 那套：状态机 / 流场 / VAT 动画 / 单点故事   │
└──────────────────────────────────────────────────────────────┘
```

**核心机制：所有层永远在跑，但只有视口附近的层被"提精度"。**

- 你在北京看着一栋楼里的 47 个人被咬 —— 上海的疫情依然在 L1 网格里每秒推进（你飞过去看到的是"已经推进到第 6 天"的状态，而不是冻结的）。
- 这个特性叫 **"世界持续性"**，是原版完全不可能有的东西，也是大地图真正的价值所在。

### 2.1 各层的存储与更新成本

| 层 | 覆盖 | 格数 | 单格状态 | 内存 | 更新频率 | GPU/CPU |
|---|---|---|---|---|---|---|
| L0 全国 | 960 万 km² | 38 万 | S/I/R/susceptible 4×f32 = 16B | 6 MB | 2 Hz | GPU compute |
| L1 省 | 10 万 km² | 160 万（250m）~960 万（1km） | 16B | 26–154 MB | 5 Hz | GPU compute |
| L2 城区 | 1,000 km² | 40 万（50m） | 人群团 32B | 13 MB | 10 Hz | CPU（Worker） |
| L3 个体 | 视口 | 2 万 | 48B | 1 MB | 20 Hz | CPU + GPU |

> 推荐实际配置：**L0 = 5km / L1 = 1km（视口 50km 内才载入）/ L2 = 50m / L3 = 个体**。

### 2.2 疫情动力学（PDE 部分）

L0/L1 用**反应-扩散模型**，不是逐个 agent：

```
∂S/∂t = -β·S·I/N + D·∇²S - v·∇S + σ(x,t)
∂I/∂t = +β·S·I/N - γ·I + D·∇²I - v·∇I
∂R/∂t = +γ·I                      （S 易感 / I 感染 / R 移除/死亡）
∂Z/∂t = +γ·I - μ·Z               （Z 尸群，独立于 SIR，会移动）
```

- `D` 扩散系数、`v` 通勤速度场（用重力模型或真实 OD 数据）、`β` 感染力（由玩家参数决定）。
- 每格 4 个 float，1 万个格的 compute shader 一次 < 0.1ms。
- **加一条"公路走廊"项**：沿高速公路的 `v` 更大 → 你会亲眼看到疫情沿着 G2 京沪高速从上海一路烧到南京。**这就是省级地图的爽点**。

## 3. 双频模拟（Dual-Frequency Simulation）

### 3.1 为什么必须双频

100 万个实体如果都按 20Hz 跑全逻辑（感知 + 决策 + 转向 + 碰撞），需要 ~2000 万次/秒的复杂更新，CPU 撑不住，而且**完全没必要**——离你 40 公里外的那个僵尸，你 20Hz 更新它和 1Hz 更新它，屏幕上完全一样。

### 3.2 双频定义

| | 快脑（Hot） | 慢脑（Cold） |
|---|---|---|
| 数量 | 视口内 ≤ 20,000 | 其余 ≤ 980,000 |
| 频率 | 20 Hz | **1 Hz**（每帧只更新 1/20 的分片，错峰） |
| 逻辑 | 完整状态机、感知、个体碰撞、感染接触、动画 | 只做三件事：**沿流场移动 / 查格子的感染概率 / 边界处置** |
| 计算位置 | CPU（WASM，多 Worker） | **GPU compute shader** |
| 状态存储 | CPU 侧 SoA + GPU 镜像 | **完全常驻 GPU**，CPU 只见位图 |

### 3.3 关键设计：**个体只读「场」，不读彼此**

这是让 100 万可扩展的最重要一条。

- 传统做法：每个僵尸查周围邻居 → 空间哈希 → O(n²) 或原子冲突 → GPU 上极其痛苦。
- **本方案**：每个僵尸只采样它所在格子的三个场值：
  1. `flowDir`（朝最近人类聚集地/新鲜尸体的方向，由 L2/L3 的流场烘焙成一张纹理）
  2. `humanDensity`（该格的人类密度）
  3. `infectionPressure`（该格的感染压力）

行为逻辑变成无分支的 5 行 shader：

```glsl
// 100 万僵尸的运动：一个 compute shader 就够
vec2 f    = texture(flowTex, pos / worldSize).xy;        // 流场方向
float den = texture(humanTex, pos / worldSize).r;        // 人类密度
float inf = texture(infTex,  pos / worldSize).r;         // 感染压力
vec2 steer = f * 1.0
           + (jitter(seed, tick) - 0.5) * 0.6            // 个体抖动，避免整齐划一
           + normalize(pos - prevPos) * 0.2;             // 惯性
pos += normalize(steer) * speed * dt;
// 感染判定：只查格子，不查邻居
if (state == 0 && inf > rand(seed + tick) ) state = 1;
if (state == 1) { timer -= dt; if (timer <= 0) state = 2; }
```

**为什么这样反而更好看**：群体行为从"个体互斥"变成"场驱动"，自然产生**拥堵、绕行、分流、汇合成河流**的效果——这正是蚁群/交通流的形态，视觉上比标准 boids 更像"尸潮"。

**代价**：个体之间不会真的"互相推挤"。但在这个尺度上没人看得出来，而且 L3 层（近处）仍然保留真实的个体碰撞。

### 3.4 状态同步：只传位图

```
CPU（WASM 决策层）                    GPU（运动层）
   │                                      │
   │  每 100ms 上传一次：                  │
   │  stateBitmap  ← 1M × 1 byte = 1MB     │
   │  (0 平民 1 潜伏 2 丧尸 3 尸体)        │
   ├─────────────────────────────────────►│
   │                                      │ 每帧积分位置（GPU 内部，零回读）
   │  每 500ms 读回一次（可选，仅统计）：   │
   │◄─────────────────────────────────────┤
   │  reduction 结果：各状态计数（几 KB）   │
```

- **位置永远不回到 CPU**（除非要存档/实体化）。
- CPU 每 100ms 上传 1MB → 10MB/s，可忽略。
- 统计通过 GPU reduction（并行归约）得到，只读回几个数字。

> **这一条是整个 v2 的性能命门**：只要不做 GPU→CPU 的位置回读，100 万就没问题；一旦回读（比如"我要给每个僵尸算 AI"），立刻掉到 2 万。

## 4. 实体化与退化（Materialize / Dematerialize）

这是"统计 → 个体"的接缝，也是整个架构里**最容易出 bug 的地方**。

### 4.1 规则

```
相机进入某区域（视口半径 < 2km）
   │
   ├─ 从 L2/L1 的密度场里"抽样"生成具体个体
   │     · 每格的 population 字段 = 该格应有个体数
   │     · 抽样时从该格扣减账面人口（守恒账本！）
   │     · 从 POI 表里给每个个体分配"家/工作地/目标"
   │
   ▼
个体在世界里真实存在（L3 全逻辑运行）

相机离开
   │
   ├─ 把个体按位置"融回"密度场
   │     · 统计各状态数量，累加回对应格
   │     · 从个体表移除
   ▼
密度场继续推进
```

### 4.2 守恒账本（必须做，否则会出现"人口凭空消失"）

每个 L2 格维护：

```ts
interface Cell {
  populationReal: number;    // 已实体化的个体数
  populationStat: number;    // 统计池里的"抽象人口"
  populationTotal: number;   // = real + stat，恒定（除非有生死）
}
// 每条 import/export 都写日志，每 5 秒全局校验：
// Σ(real) + Σ(stat) === 初始总人口 - 死亡数
```

**验收**：跑 10 分钟，来回缩放 20 次，人口账本误差必须为 **0**。这条写成单元测试。

### 4.3 接缝的视觉处理

实体化/退化发生时，个体与统计点之间要**无缝**：

- 退化时：个体的点先缩小到 1px 再消失，同时密度场的格子亮度补偿一下（视觉上"融进去了"）。
- 实体化时：反过来。
- **关键**：阈值要按"屏幕像素尺寸"算，而不是按距离。当个体屏幕尺寸 > 3px 时实体化，< 1.5px 时退化 —— 中间留 1.5–3px 的滞回带，防止在边界反复横跳。

## 5. 渲染：三档 LOD + 密度累积

### 5.1 三档

| 档 | 触发条件 | 方案 | 数量级 | 成本 |
|---|---|---|---|---|
| **A 个体** | 屏幕尺寸 > 3px | VAT 人形（v1 §8.3） | ≤ 20,000 | 3–5ms |
| **B 人群块** | 1.5px < 尺寸 < 3px | 点精灵 quad（带方向拉伸，像雨点） | ≤ 200,000 | 1–2ms |
| **C 密度场** | 尺寸 < 1.5px | **GPU 累积成纹理** | 800,000+ | < 1ms |

### 5.2 档 C 的做法（这是百万级的核心技巧）

```
1M 个点 → rasterize 到一个 1024×1024 的 R16F 累积缓冲（加法混合）
        → 一次 mipmap/blur
        → colormap（青→黄→白，或者原版的绿→红）
        → 作为一张全屏 quad 叠在底图上
```

- 一次 draw call，1M 个点，**全部在 GPU 上，CPU 零参与**。
- 效果：省级视角下你看到的是**流动的、有质感的"感染云"**，比 100 万个抖动的点好看得多，也更可读。
- 叠加：`bloom` 让密集处发光，密度梯度自然显出"潮水的方向"。

### 5.3 中间档 B 的必要性

如果 A 直接跳 C，会有视觉断层（从"人"突然变成"雾"）。档 B 的**点精灵**是过渡：给每个点加一个朝向速度方向的短拖尾（速度拉伸的 quad），远看像一群流动的虫子 —— 这一档最像"尸潮"。

### 5.4 性能预算（1M，4K，60fps）

| 项 | 预算 | 说明 |
|---|---|---|
| GPU compute（运动 1M） | 0.3 ms | 每帧 1M × ~50 flops = 50 MFLOP，1% 都不到 |
| 档 C 密度累积 | 0.6 ms | 1M 点 × 1px 有效面积 |
| 档 B 点精灵 ≤ 20 万 | 1.2 ms | 4px quad，含 overdraw |
| 档 A 人形 ≤ 2 万 | 4.0 ms | VAT + 实例化 |
| 城市几何（视口内 ≤ 1km²） | 3.0 ms | 合并静态 |
| 后处理 | 2.5 ms | 合并成单 pass |
| 底图（PMTiles 矢量，30fps 刷新） | 1.5 ms | |
| **合计** | **≈13 ms** | 60fps 有余量 |

> 注意：**真正的风险不是算力，是带宽**。1M 位置 = 8MB，每帧读写就是 960MB/s；用 `storage buffer` 在 GPU 上原地更新（ping-pong 两个 buffer）即可，千万不要每帧上传下传。

## 6. 地图数据：金字塔 + PMTiles

### 6.1 分层数据

| 层级 | 数据 | 来源 | 体积估计 |
|---|---|---|---|
| L0 全国 | 行政区划、主要城市点位、人口栅格（5km） | OSM + **GHSL/WorldPop** | 20–50 MB |
| L1 省级 | 路网（高速/国道/铁路）、水系、城市建成区面 | OSM（Geofabrik 省 extract） | 200–600 MB（PMTiles 压缩后） |
| L2 城区 | 街道级路网、建筑轮廓（仅算面积/高度分布，不建几何） | OSM | 按需 |
| L3 街区 | 完整建筑几何 + POI + 树木 | OSM（v1 §4 管线） | 每个 1km² 约 20–60 MB |

### 6.2 存储格式：**PMTiles**

- 单文件、范围请求友好、无服务器依赖、可以直接放本地磁盘。
- 用 `pmtiles` 的 JS 读取器 + `@mapbox/vector-tile` 解码，自己写一个极简瓦片渲染器（或者直接把 PMTiles 喂给 MapLibre 当底图）。
- **关键**：L1 的路网不是用来"看"的，是用来**驱动 PDE 的传播通道**和**让个体沿路移动**的。所以必须解析成图结构（节点 + 边 + 车道数 + 限速）。

### 6.3 人口数据（这是省级玩法的灵魂）

- **GHSL GHS-POP**（1km 全球，公开，2020 版）：直接给出"每个 1km 格里住了多少人"。
- 全国 960 万格 × 1 人分辨率 → 你能真实地算出"疫情从武汉扩散到郑州需要几天"。
- **默认参数校准**：真实中国人口密度、真实城市规模 → 玩家一开局就是"真实的中国"，而不是一个玩具沙盘。

### 6.4 英雄城市（L3 数据的来源）

不可能全国都是精细几何。做法：

1. 预烘 3–5 个城市（建议：**华盛顿特区**致敬原作 + **你所在的城市** + 一个高密度特大城市如上海/北京）。
2. 每个城市 2–4 km²（够看、够玩），用 v1 的 OSM 管线烘焙，每个 20–60MB。
3. 允许"即席烘焙"：给任意地址，跑一次 Python 脚本（5–20 分钟）生成新的英雄片区。

> 这就是"任意地点"的现实版本：**省级任意、街区级限量**。

## 7. 玩法重构（三层 + 无缝缩放）

### 7.1 缩放即玩法

| 缩放级别 | 视野 | 你能看到 | 你能做 |
|---|---|---|---|
| **L0 战略**（省/国） | 数百公里 | 疫情云、城市失守时间表、公路传播线 | 全国政策：封城、断高速、军队集结、疫苗分配 |
| **L1 战役**（城市） | 10–50 km | 街区级扩散、难民车流、检查站 | 部署路障、设卡、空袭、撤侨 |
| **L2 战术**（街区） | 0.5–2 km | 具体的人、警匪交火、尸潮 | 空投、直升机救援、定点轰炸（原版那套） |
| **L3 故事**（个人） | < 100 m | 一个人的脸、他的家人、他被咬的瞬间 | 只能看（这是原版的灵魂，不能动） |

**滚轮从"整个省"一路推进到"一个人的脸"，中间没有加载画面、没有模式切换。** 这是 2009 年做不到、也是这个复刻项目最有价值的一件事。

### 7.2 宏观层的"好玩"问题（最大的非技术风险）

必须承认：**看一张红色的云图扩散，10 分钟就腻了。** 所以 L0/L1 必须有决策压力：

- **时间压力**：疫情每 tick 在涨，你的资源在减。
- **决策不可逆**：封城会引发恐慌外逃（反而加速扩散），不封会指数增长。
- **信息不全**：你只看到"报告上来的数字"，实际数字有延迟和瞒报（可以做成机制：真实值 vs 报告值的差）。
- **结算**：死亡人数、失守城市数、幸存率 → 评分。

**这条必须先做原型验证（M5）**，如果宏观层不好玩，就把重心压回 L1/L2，L0 只做"背景板"。

### 7.3 保留 v1 的所有细节玩法

单点追踪、镜头导演、热成像、2009 复古模式、行动后报告 —— 全部保留，但**它们只在 L2/L3 生效**。复古模式在省级视角下就变成了"2009 年那个点阵地图"，反而更有味道。

## 8. 确定性的降级（必须明确声明）

v1 里我承诺了"全链路确定性"。**v2 必须放弃它的一部分**，原因是 GPU compute 的原子操作/并行归约天然非确定（顺序不定 → 浮点累加顺序不定 → 结果有微小差异 → 长跑后分叉）。

### 8.1 新的确定性契约

| 层 | 确定性 | 说明 |
|---|---|---|
| L0/L1 PDE | ✅ **严格确定** | 纯 CPU 或确定序 GPU（固定 tile 顺序 + 无原子） |
| L2 人群团 | ✅ **严格确定** | CPU，固定序 |
| L3 个体（快脑） | ✅ **严格确定** | CPU，同 v1 |
| 远景点云（慢脑） | ❌ **非确定** | GPU 并行，允许 ±0.1% 分叉 |

### 8.2 回放怎么做

- 存档 = **L0/L1/L2 的完整状态（几 MB）+ 种子 + 干预事件**。
- 回放时点云从 PDE 场重新抽样 → 视觉上与原来几乎一致（因为个体行为本来就是随机的）。
- **"剧情级"事件（谁死了、哪个城市失守、曲线形状）100% 可复现**，"某个远处僵尸的精确轨迹"不复现。对自用项目，这是完全可接受的。

## 9. 技术栈重选

| 层 | v1 方案 | v2 方案 | 理由 |
|---|---|---|---|
| 渲染 | Three.js (WebGL2) | **Three.js + WebGPU 后端**（或直接写 WebGPU） | 100 万粒子需要 compute shader；Three 的 `WebGPURenderer` 已可用 |
| 宏观计算 | — | **WebGPU compute**（PDE、流场、粒子） | GPU 天生适合网格计算 |
| 个体决策 | TypeScript | **Rust → WASM**（SIMD128 + 多 Worker） | 20 万个体的状态机，JS 撑不住但 WASM 轻松 |
| 地图 | MapLibre | **MapLibre（只用于 L1 底图） + 自写 PMTiles 读取器** | 全国路网用矢量瓦片 |
| UI | React | React（不变） | |
| 数据管线 | Python | Python（不变）+ PMTiles 工具链 | |
| 打包 | Vite | Vite + `vite-plugin-wasm` | |

### 9.1 Web 还是原生？（重要决策）

| | Web（WebGPU + WASM） | 原生（Rust + wgpu） |
|---|---|---|
| 迭代速度 | ⚡ 秒级热更 | 🐢 分钟级编译 |
| 100 万粒子性能 | 原生的 **85–95%** | 100% |
| 内存上限 | 浏览器标签页 ~4GB | 无限 |
| 大地图流式 | 要自己写 + 受限于 fetch | mmap，直接读 |
| 分享 | 一条链接 | 要打包分发 |
| 调试 | DevTools + 图形调试 | RenderDoc 更强 |

**建议：仍然走 Web**，理由：

1. 百万级的瓶颈在 GPU，浏览器 WebGPU 能吃到 85–95%；
2. 内存够用（数据是压缩+流式的，热数据 < 1GB）；
3. **迭代速度对个人项目是生死线**；
4. 架构上把 Rust 内核编译成 WASM 和原生两个 target，真到了需要原生的那天，**只换壳不重写**。

## 10. 里程碑（重排，先验证最危险的东西）

### M0 · 百万粒子验证（2–3 天）⚡ 最高风险

- [ ] CPU 占用 < 15%（证明零回读）
- [ ] 密度场视觉上"像尸潮"（有方向、有明暗、有流动）

**若失败**：直接降到 30 万或改用纯点精灵，重新评估整个 v2。

### M1 · 全国人口栅格 + PDE 传播（1 周）

- GHSL 数据导入，5km 全国网格，SIR + 扩散 + 公路走廊。
- 视觉：一张会动的全国疫情图。
- **验收**：从武汉点火，30 天后全国疫情分布与真实人口密度高度相关。

### M2 · 实体化 / 退化 + 守恒（1 周）

- 缩放时个体 ↔ 统计的转换，人口账本零误差。
- **验收**：来回缩放 20 次，账本误差 = 0。

### M3 · L3 个体层（1–2 周）

- 把 v1 的 §4/§7/§8.3 搬进来：OSM 建筑、VAT 人形、流场、状态机。
- **验收**：街区视角能跟着一个人看完他被咬的全过程。

### M4 · 无缝缩放（1 周）

- 四层 LOD 的相机、数据流式、交互集切换。
- **验收**：从 800km 视野滚到 5m 视野，无卡顿、无加载条、无视觉断裂。

### M5 · 三层玩法原型（1–2 周）

### M6 · 英雄城市（1 周）

### M7 · 叙事、报告、回放、复古模式（1 周）

## 12. 需要你拍板

1. **"100 万"的定义**：你要的是 ① 屏幕上有 100 万个发光的点（视觉百万，成本极低），还是 ② 100 万个真实存在、会跨城传播的实体（架构级，本报告方案）？**我建议 ②，但它需要 M0+M2 都通过。**
2. **地图范围**：先做**一个省**（推荐，1–2 个月能完整），还是直接上全国（+1 个月，且内存/流式压力翻倍）？
3. **原生还是 Web**：接受 WebGPU（迭代快，性能 85–95%），还是直接上 Rust 原生（性能拉满，迭代慢）？
