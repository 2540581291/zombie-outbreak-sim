两件事：尺寸不写死 + 每格统一到原版的 0.44m

一、原版地图尺寸并非都一样，脚本改成"从资源推"
  我们手上这份 2009 SWF 只带了莱斯特这一张图，所以看起来是固定值；
  但 Class 3 Outbreak / 手游版是另外的图（尺寸、瓦片数都不同）。
  tools/pull_original_map.py 现在全部从数据推：
    PX   = 读第一张瓦片图的实际边长
    S    = sqrt(瓦片数)              （324 → 18）
    P    = 288 // S                  （缩略图上每块占多少像素）
    GRID = sqrt(碰撞表字节数)         （1,327,104 → 1152）
    CELL = (S*PX / GRID) * 0.11      （每格像素 × 米/像素 → 0.44m）
  实测仍是 324 张 / 4608x4608 / 1152 格 / 0.44m / 506.9m。

  我们自己城市的尺寸本来就不是写死的：city.json 的 size 来自 bbox × 米/度。

二、每格统一 0.44m（= 原版标准），默认值已改
  pipeline/collision.py  build(cell=0.44)
  pipeline/bake_pbf.py   --cell 默认 0.44
  js/main.js             兜底 buildNav(city, 0.44)

  代价（格数是平方增长）：

    地图      0.44m                          1.0m
    莱斯特    1.33M 格 / 解压 1MB / 门场 15MB   0.26M / 0MB / 3MB     ✅ 轻松
    柏林      39.2M 格 / 解压 37MB / 门场 449MB  7.59M / 7MB / 87MB    ⚠️ 门场降级
    东京      51.6M 格 / 解压 49MB / 门场 591MB  10.0M / 10MB / 114MB  ⚠️ 门场降级

  "门场降级"指超过 2000 万格时 buildDoorField() 自动跳过（否则 3 个 Int32 数组
   会到 500MB+），代价是屋内寻路退化成 doorGradient 近似。
  烘焙耗时也会涨（柏林 0.4m 实测 230 秒，1m 是 35 秒）。

  现有 data/cities 里的碰撞表还是 1m 烘的，改默认值不会自动重烘，
  要让柏林也变 0.44 得重跑 bake_pbf.py（约 4 分钟 + 门场降级）。
